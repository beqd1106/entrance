# Houserule 企画書

> 全国の雀荘が「オンライン支店」を持つプラットフォーム
> 試作アプリ同梱版（2026年8月）

---

## 1. 現状整理

いただいた相談を整理すると、要望は次の6層に分かれています。

| 層 | ご要望 | 本質 |
| --- | --- | --- |
| ゲーム | 雀魂の簡易版／四麻のたたき台／CPU対戦 | **入口の道具**であって目的ではない |
| ルール | ハウスルールで対戦したい／サンマの店内勉強用アプリ | 店の個性＝ハウスルールを扱えることが核心 |
| コミュニティ | 店ごとにネット上でコミュニティ／客同士でも対戦 | 店の「人」に触れる場 |
| 記録 | 成績管理・ポイント機能 | 継続来店の動機づけ |
| 体験 | 未来店の人がハウスルールの感触を確かめられる | **来店前の不安の解消**（最重要） |
| 事業 | 全国の雀荘がオンライン支店を持つプラットフォーム | 店舗送客のインフラ |

すでに手元にあるもの：サンマの店内勉強用アプリを作れる目処。
つまり「麻雀ロジックを書ける」ことは前提として立っています。
**足りないのは、ロジックではなく“店ごとにルールを差し替えられる構造”と“来店導線”です。**

---

## 2. この企画の本質

これは麻雀アプリではなく、**雀荘の集客・体験設計プロダクト**です。

一般ユーザーが初めての雀荘に行かない最大の理由は「強さへの不安」ではなく、
**「その店のルールと空気が分からない」不安**です。

- 白ポッチって何？　抜いた北はどうなる？
- 五等サンマって、どういう点数の動き方をするの？
- 知らないルールで自分だけ損しないか？
- 常連ばかりで浮かないか？

この不安は、ルールを**読ませても**消えません。**打たせると**消えます。

> Houseruleは「その店のルールで実際に1半荘打てる」ことを、来店前の標準体験にします。

## 4. 一言コンセプト

> **その店のルールで、行く前に打てる。**
> 全国の雀荘が持つ、オンライン支店。

副次コピー：

- 「ルールを読む」から「ルールで打つ」へ。
- 初来店の不安を、1半荘で消す。

## 5. 解決する課題

### ユーザー側

1. **ルールが分からないから行けない** — 店ごとに違い、Web上の表記も断片的。
2. **失敗が怖い** — 知らないローカルルールで場を止めたくない。
3. **雰囲気が分からない** — 常連度・客層・スタッフが事前に見えない。
4. **練習の場がない** — 特殊ルールは練習しようがない（雀魂にもMJにも無い）。

### 店舗側

1. **新規客が入ってこない** — 常連の高齢化・固定化。
2. **ルールを説明するコストが高い** — 毎回スタッフが口頭説明。
3. **ルールの独自性が伝わらない** — 差別化要素なのに、伝える手段がない。
4. **オンライン施策の手段がない** — SNSはあるが「体験」を渡せない。
5. **来店前教育ができない** — 初心者を歓迎したいが、教える工数が出せない。

### 市場構造の課題

- 既存の雀荘検索サイトは「場所・料金・レート」で探すが、**ルールで探せない**。
- ネット麻雀（雀魂・MJ・Maru-Jan）は標準ルール一択で、**ローカルルールは扱わない**。
- 結果、**ローカルルールという最大の個性が、集客資産になっていない**。

## 6. 目指す体験

```
① 店を発見（ルール条件で検索）
        ↓
② ルールを見る（一般ルールとの差分だけ表示）
        ↓
③ ハウスルールを体験する ← ここが本サービスの中心
        ↓
④ 店の雰囲気・スタッフ・料金を知る
        ↓
⑤ オンラインで交流する（将来：店別ルーム／観戦／配信）
        ↓
⑥ 興味を持つ
        ↓
⑦ 実店舗へ来店する（QRチェックイン）
```

③ で「知らないルールを1回でも打った」状態を作ることが、⑦ への転換率を決めます。
現在の試作は ①〜④ と ⑦ の記録部分までを実装済みです。

## 7. ターゲットユーザー

| セグメント | 状態 | Houseruleで解決すること |
| --- | --- | --- |
| **初心者・復帰勢**（最重要） | 雀魂は打つが実店舗は未経験 | 「知らないルールで恥をかく」不安を事前に消す |
| 旅打ち・遠征層 | 出張先や旅行先で打ちたい | 現地の店のルールを事前に把握して即打てる |
| 三麻好き | 地域ごとの三麻の差が大きい | 五等サンマ系など、その店の系統を事前に確認 |
| ローカルルール愛好層 | 特殊牌・祝儀ルールが好き | 特殊ルールで店を横断検索できる |
| 常連 | すでに通っている | オンライン支店での交流・記録・称号 |

初期のコアターゲットは **「雀魂は打てるが実店舗未経験の20〜30代」** に置きます。
理由：人数が多く、不安の内容が明確で、施策で動かしやすいためです。

## 8. ターゲット店舗

**フェーズ1（PoC）**

- ノーレート／低レートの健全店
- 初心者歓迎を掲げている店
- ハウスルールに個性がある店（特殊牌・祝儀ルール・特殊三麻）
- SNS運用に前向きな店
- 個人経営で意思決定が速い店

**フェーズ2**

- 複数店舗チェーン（横展開しやすい）
- セット中心店（ルール説明コストが特に高い）
- 大会・イベントを打っている店

**当面は狙わない**

- 高レート店（法務リスクの管理が難しい）
- ルールが完全に標準で差別化要素がない店（提供価値が薄い）

---

## 9. 差別化ポイント

1. **ルールが「データ」である** — 店の設定を差し替えるだけで、対局の挙動・点数・祝儀・説明文がすべて変わる。ゲーム側に店名の分岐が一切ない。
2. **未知のルールに後から対応できる** — 特殊牌エンジン＋WHEN/IF/THENのカスタムルールにより、開発者が知らないハウスルールでも設定だけで追加できる。
3. **「読む」ではなく「打てる」** — 検索サービスでもルールDBでもなく、体験そのものを渡す。
4. **一般ルールとの差分表示** — 全文を読ませない。「この店が普通と違うのは19項目だけ」と示す。
5. **説明文の自動生成** — 店が設定すると、初来店者向けの説明文が自動で出来上がる。店側の運用コストがゼロに近い。
6. **矛盾チェック（Rule Validator）** — 自由度を上げても設定事故が起きない。警告は出すが、意図的な上級設定は通す。
7. **非換金設計を最初から内蔵** — ポイントはゲーム内専用。法務リスクの高い設計を構造的に作れないようにしてある。

## 10. 雀魂や既存検索サービスとの差

| | 雀魂・MJ・Maru-Jan | 雀荘検索サイト | **Houserule** |
| --- | --- | --- | --- |
| 目的 | オンラインで遊ばせ続ける | 店舗情報を引く | **実店舗へ送客する** |
| ルール | 標準ルール固定 | テキストで羅列（店により未記載） | **データとして定義され、実際に動く** |
| ローカルルール | 非対応 | 記載のみ | **体験できる** |
| 収益源 | 課金（ユーザー） | 掲載料 | **店舗のサブスク＋送客** |
| 滞在時間 | 長いほど良い | 短い | **短くてよい（来店が成功）** |
| 競合関係 | — | 一部競合 | 雀魂とは**非競合**（練習後の受け皿） |

**重要な立ち位置**：雀魂と戦わない。
雀魂で麻雀を覚えた人が「実店舗デビューする時に開くアプリ」というポジションを取ります。

## 12. 最初に選ぶべきMVP

### 選定：**D案（Playable四麻＋店舗ルールプリセット＋店舗ページ）**

理由：

1. **提案の場で価値が伝わるのはDだけ**。資料10枚より「触ってください」の30秒が強い。
2. B案（1店舗限定）は最短に見えて、2店舗目で必ず作り直しになる。
   最初からルールをデータ化しておけば、2店舗目以降は**設定の追加だけ**で済む。
3. A/C案は「ルールが本当に動くのか」という最大の技術リスクを先送りする。
   Dはそのリスクを最初に潰す。
4. 今回、**Dはすでに実装済み**（本リポジトリ）。次の投資判断を実物を見ながら行えます。

## 15. ルール調査方針

### 調査済みの範囲と情報源

| 対象 | 主な参照 | 実装への反映 |
| --- | --- | --- |
| アリス | 麻雀ローカルルールWiki、麻雀豆腐 | 門前和了時にドラ表示牌の隣（槓ドラ位置）をめくり、手牌に同じ牌があれば祝儀、一致する限り継続。リーチ必須の流派もあるため設定化 |
| チューリップ | 麻雀ローカルルールWiki | 「現物＋その両隣も対象」の拡張。アリスとは別設定として独立 |
| 白ポッチ | 麻雀ローカルルールWiki（Fandom）、麻雀プレス | 白4枚のうち1枚に赤い点。リーチツモ時にオールマイティ扱いが最多 |
| 五等サンマ系 | note（複数の実践者記事）、麻雀訪問記 | 35,000持ち40,000返し／萬子2〜8抜き／常時ドラ2枚／5筒5索が金金赤赤／北は抜きドラ／華牌の効果（春＝即時祝儀、夏＝打点1ランクアップ、秋＝5がダブドラ、冬＝アリス）／ツモ損の有無／完全順位制＋沈みウマ／サイコロチャンス（四北・四華・本役満などで発動、ゾロ目・ピンゾロ倍率） |
| 宝石牌（Jewel型） | 店舗紹介記事・実践者記事 | 牌ごとに異なる効果（ドラ+2／祝儀+n／オールマイティ／翻数倍化など）を持つ体系。**効果の組み合わせで表現できる汎用エンジン**として実装 |
| 割れ目・焼き鳥・オープンリーチ・北抜き | 各ローカルルール解説 | すべて設定項目化 |

### 方針

1. **既知ルールを列挙するのではなく、ルールの“文法”を定義する**。
   （枚数／条件／効果／タイミング／対象）の5要素に分解すれば、未知のルールも表現できる。
2. **1店舗の実装をしない**。「五等サンマを実装する」ではなく「五等サンマ系を作れるエンジン」を作る。
3. **実在店舗のルールは無断使用しない**。デモは架空店舗で構成し、実店舗導入時はヒアリングして設定する。
4. **流派差は仮置きし、README に明記する**。ヒアリングで差し替えられる形にしておく。

## 17. ルールエンジン設計

### レイヤ構造

```
Store Rule Preset      店舗が保存した設定（＝ただのデータ）
        ↓
Rule Configuration     全設定項目のスキーマ＋既定値（defaults.js）
        ↓
Rule Engine            BasicRules / DoraRules / YakuRules /
                       SpecialTileRules / BonusRules / CustomRules
        ↓
Game Engine            TileEngine / TurnEngine / ActionEngine /
                       HandEvaluator / ScoreEngine
```

### 実装上の絶対原則

- **ゲームエンジンは店名を知らない。** `if (店 === 'A店')` のような分岐をコードに書かない。
- 店舗ごとの違いは、すべて `rules` オブジェクトの差分として表現する。
- 新しい店を追加する作業＝**JSON相当のデータを1件足すだけ**（コード変更ゼロ）。

### 検証方法

同じエンジンに17種類のプリセットを流し込み、CPU自動対局で挙動が変わることを確認済みです。

| プリセット | 平均翻 | 特徴的な発生 |
| --- | --- | --- |
| 競技ルール風（赤なし・一発裏なし） | 2.47 | 祝儀0 |
| 一般四麻（赤3） | 3.27 | — |
| 特殊牌館 | 4.40 | 特殊牌の効果・サイコロ発動 |
| 五等サンマ館 | 6.90 | 華牌ランクアップ258回・アリス220回・サイコロ171回 |
| 花牌重視五等 | 8.19 | 秋のダブドラで打点が跳ね上がる |

## 18. 特殊牌エンジン設計

### 定義の形

```json
{
  "id": "blue5s",
  "name": "青5索",
  "tile": "5s",
  "count": 1,
  "color": "blue",
  "effects": [
    { "type": "bonus", "value": 2 },
    { "type": "dora", "value": 1 }
  ],
  "conditions": { "menzenOnly": true }
}
```

### 効果（effects）

| type | 意味 |
| --- | --- |
| `dora` | ドラ +n |
| `han` | 翻数 +n |
| `bonus` | ゲーム内ポイント +n |
| `rankUp` | 打点ランクアップ（満貫→跳満→倍満…） |
| `almighty` | オールマイティ牌として和了に使える |
| `doubleDora` | 指定牌をダブルドラ化 |
| `bonusMultiply` | 獲得ボーナスを ×n |
| `yakuman` | 役満扱い |

### 条件（conditions）

門前限定／リーチ時限定／ツモ限定／ロン限定／一発時限定／副露時無効／
**combo（複数の特殊牌が揃った時のみ有効）**

### House Rule Builder（WHEN / IF / THEN）

未知のルールは、条件式として後から追加できます。

```json
{
  "name": "オールスター（特殊牌3種以上）",
  "when": "win",
  "if": [
    { "fact": "hasSpecial", "id": "blue5s" },
    { "fact": "hasSpecial", "id": "silver5p" },
    { "fact": "hasSpecial", "id": "emerald5m" }
  ],
  "then": [
    { "action": "bonus", "value": 10 },
    { "action": "rankUp", "value": 1 },
    { "action": "dice" }
  ]
}
```

使える `fact`：hasTile／hasSpecial／menzen／tsumo／ron／riichi／ippatsu／han／yakuman／dealer／kita／flower
使える `action`：bonus／han／dora／rankUp／points／dice／message

> これにより「開発者が知らないハウスルール」も、コードを触らずに表現できます。

### 共通の骨格（GOTO_BASE）

| 牌 | 既定の効果 | 変更可能な範囲 |

## 23. CPU仕様

**強さは目的ではありません。「ルールを体験させる相手」として自然であれば十分です。**

| 項目 | 実装 |
| --- | --- |
| 手作り | 向聴数を最小化。同値なら受け入れ枚数の広い方を選択 |
| 牌の価値 | ドラ・赤・金・白ポッチ・特殊牌は残す方向に重み付け |
| リーチ判断 | 待ちの残り枚数と打点（ドラ数）で判断。危険時は愚形リーチを見送る |
| 鳴き判断 | 向聴が進む＋役の目処（役牌・喰いタン可否）がある時のみ。三麻ではチーなし |
| 守備 | 他家のリーチ・3副露以上を危険度として検出し、現物＞字牌＞端牌＞筋の順に選択。押し引きは向聴数で切替 |
| 三麻対応 | 北抜きを自動判断（国士系の手なら抜かない） |
| 難易度 | 初心者／標準／上級の3段階（リーチ基準・鳴きの緩さ・ベタオリ閾値・受け入れ重みが変化） |

将来：牌譜からの学習、店ごとの「常連っぽいCPU」（キャラクター化）へ拡張可能な構造にしてあります。

## 27. 法務・運用リスク整理

> **以下は論点の整理であり、法的助言ではありません。実施前に必ず弁護士等へご確認ください（要専門家確認）。**

| リスク | 内容 | 本試作での扱い |
| --- | --- | --- |
| **賭博罪（刑法185条等）** | 財物・財産上の利益を賭ける行為。オンライン麻雀に金銭性を持たせると該当リスク | 金銭・賭け金の概念を**実装していない** |
| 対局結果への金銭・景品付与 | 結果に応じた報酬は賭博性を帯びやすい | 対局結果に対する**外部価値の付与なし** |
| 換金性ポイント | 換金・譲渡・売買可能なポイントは特にリスクが高い | BPは**非換金・譲渡不可・ゲーム内専用**。表示にも「非換金」を明記 |
| イベント報酬 | 賞品の価値・提供方法によっては景品表示法の景品規制 | MVPでは**ゲーム内称号・バッジのみ**（物品なし） |
| 景品表示法 | 有利誤認・優良誤認、総付景品・懸賞の限度額 | 実店舗の料金・特典表示は店舗側の責任範囲を明確化。誇大表現を置かない |
| 資金決済法 | 前払式支払手段（未使用残高が一定額を超えると届出等） | **有償ポイントを発行しない**設計 |
| 風営法 | 実店舗（麻雀店＝5号営業）は許可制。オンライン側は原則対象外だが、実店舗誘導との関係整理が必要 | 掲載は**許可を得た営業店舗のみ**を前提。レート表記は掲載しない方針 |
| 未成年利用 | 実店舗は18歳未満入店不可が通例 | 年齢確認と、未成年への来店導線の抑制を運用要件に |
| 本人確認 | 対人対戦・複アカ対策で必要になり得る | フェーズ3（オンライン対戦）で検討。MVPでは不要 |
| 依存対策 | 長時間利用・射幸性 | プレイ時間の表示、連続プレイの抑制表示、相談窓口の掲示 |
| 不正・談合・複アカ | 人間同士の対戦で発生 | **MVPではCPU対戦のみ**にすることで構造的に回避 |
| 個人情報保護 | 会員情報・来店履歴・位置情報 | 収集を最小化。来店記録は店舗単位の回数のみ。プライバシーポリシー整備 |
| 著作権・商標 | 実在店舗名・ロゴ・ルールの掲載 | デモは**すべて架空店舗**。実装時は店舗の許諾を取得 |

### 特に注意すべき点

1. **「ポイント」という言葉の危うさ**
   換金しなくても、「オンラインのポイントで店の飲食が無料になる」等は景品規制の検討対象になり得ます。
   MVPでは**店舗の実利益と結びつけない**でください。
2. **オンラインの成績と実店舗の特典を直結させない**
   （例：「オンラインで1位を取ると店で割引」は避け、「来店回数で称号」など**行動ベース**に留める）
3. **レート表記をしない**
   掲載店舗は「ノーレート」または表記なしで統一するのが安全側です。

| 5 | イベント支援 | 大会運営・集計・告知 | 都度 | フェーズ3 |
| 6 | 白ラベル提供 | チェーンへの独自ブランド提供 | 要相談 | フェーズ4 |
| 7 | 練習アプリのOEM | 店内の勉強用アプリとして提供 | 月額 | 随時 |

**ユーザー課金は当面しない**方針を推奨します。
無料であるほど送客が増え、店舗の支払意欲が上がる構造だからです。

想定：1店舗あたり月1万円 × 100店舗＝月100万円。まず**5〜10店舗**での成立を検証します。

## 34. 実際に動くアプリの実装方針

1. **最短で触れることを最優先**。npm install もビルドも不要。`start.bat` のみ。
2. **エンジンとUIを完全分離**。エンジンは `src/`、画面は `web/`。エンジンはDOMを知らない。
3. **テストと本番で同じコードを使う**。テストが通る＝画面でも同じ挙動。
4. **ルールは全部データ**。店の追加＝データ1件の追加。
5. **決め打ちを避け、仮定はREADMEに書く**。流派差はヒアリングで差し替える前提。
6. **法務の安全側をコードに埋め込む**。金銭概念を実装しない。ポイントは非換金表記を強制。
