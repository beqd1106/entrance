# Entrance 技術設計書

---

## 1. 設計の中心にある一文

> **ゲームエンジンは、店の名前を一切知らない。**

店舗ごとの違いは、すべて `rules` というデータの差分として表現されます。
`if (店 === 'A店')` のような分岐はコード上に1つも存在しません。
新しい店の追加＝**データを1件足すだけ**（コード変更ゼロ）です。

## 3. データ構造

### 3-1. 牌（Tile）

```js
{ id: 42, t: 22, red: false, gold: true, dot: false, sp: 'blue5s', flower: null }
```

| フィールド | 意味 |
| --- | --- |
| `id` | 山の中で一意。**牌の同一性**の担保に使う（テストで重複を検出） |
| `t` | 牌タイプ 0〜37 |
| `red/gold/dot` | 赤牌／金牌／白ポッチ |
| `sp` | 特殊牌の定義ID（`rules.specialTiles[].id`） |
| `flower` | 華牌の種類（spring/summer/autumn/winter） |

牌タイプの割当：

```
 0- 8 : 1m-9m      9-17 : 1p-9p      18-26 : 1s-9s
27-33 : 東南西北白發中
34-37 : 春夏秋冬（手牌構成に参加しない。抜いて即補充）
```

**設計意図**：属性（赤・金・特殊）を牌タイプから分離したことで、
「青い5索」「金の5筒」「赤い点の白」を、役判定ロジックを変えずに表現できます。

### 3-2. ルール設定（RuleConfig）

トップレベルの構造：

```js
{
  meta:    { id, name, description, autoFixed[] },
  game:    { players, length, agariYame, tobiEnd, westEntry, ... },
  scoring: { startingPoints, returnPoints, useFu, roundUpMangan,
             countedYakumanHan, uma[], rankOnly, shizumiUma, honbaPoints, ... },
  win:     { kuitan, atozuke, kuikae, chi, pon, kan, furitenRiichi,
             formalTenpai, ankanAfterRiichi, doubleRon, minHan, ... },
  renchan: { dealerRepeat, kyuushuKyuuhai, suufonRenda, suukaikan, ... },
  ryuukyoku:{ notenPenalty, nagashiMangan },
  dora:    { indicators, ura, kanDora, kanUra, red{}, gold{}, permanentDora[], ... },
  local:   { shiroPocchi{}, openRiichi{}, wareme{}, alice{}, tulip{},
             dice{}, yakitori{}, binta{}, tobiBonus{} },
  sanma:   { removeManzu, northMode, kitaIsDora, tsumoLoss, ... },
  flowers: { enabled, tiles[], isDora, effects{spring,summer,autumn,winter} },
  specialTiles: [ ... ],
  customRules:  [ ... ],
  bonus:   { enabled, label, ippatsu, ura, aka, gold, pocchi, kita, yakuman, ... }
}
```

**プリセットは「既定値からの差分」しか持ちません。** 例：

```js
{
  id: 'store_yonma_kan',
  name: 'DEMO雀荘 四麻館 ルール',
  rules: {
    scoring: { roundUpMangan: true },
    dora:    { red: { '5m': 1, '5p': 1, '5s': 1 } },
    local:   { shiroPocchi: { enabled: true, count: 1, bonus: 2 },
               alice:       { enabled: true, bonusPerMatch: 1 } },
    specialTiles: [{ id: 'blue5s', name: '青5索', tile: '5s', count: 1,
                     color: 'blue', effects: [{ type: 'bonus', value: 2 }] }]
  }
}
```

### 3-3. 合成の規則（resolveRules）

1. 既定値と深いマージ（配列は置き換え）
2. **`dora.red` / `dora.gold` は加算ではなく置き換え**（「赤なし」を表現できるようにするため）
3. 物理的に不可能な設定は自動修正し、`meta.autoFixed` に記録
   （例：三麻で萬子2〜8を抜く設定なのに赤5萬が指定されている → 自動的に外し、エディタで警告表示）
4. 人数による強制（三麻ではチー不可 など）

### 3-4. ゲーム状態（GameState）

```js
engine = {
  rules, rng, debug,
  round:   { wind, kyoku, honba, kyotaku, dealer },
  players: [{ seat, name, isCpu, level, points, bonus, wins,
              hand[], melds[], discards[], kita[], flowers[],
              riichi, openRiichi, doubleRiichi, ippatsu,
              furiten, tempFuriten, waits[], drawn, tenpai, nagashi }],
  wall:    Wall, wareme, turn, phase, pending, kanCount, firstGoAround,
}
```

`pending` は「今、誰の入力を待っているか」を表す唯一の場所です。

```js
{ kind: 'turn',  seat }                                   // 手番（打牌・リーチ・カン・ツモ…）
{ kind: 'claim', tile, from, candidates[], responses }     // 打牌に対する反応（ロン・ポン・チー・カン）
```

### 3-5. 店舗データ

```js
{
  id, name, catch, presetId,            // presetId でルールと結合
  area, address, access, hours, smoking, tables, style,
  beginner(1-5), beginnerNote, mood[], priceLines[], staff[], events[], sns,
  photo{hue, icon}, ruleHighlights[], tags[]
}
```

店舗とルールは `presetId` で疎結合にしてあり、
**同一ルールを複数店舗で共有**することも、店舗ごとに固有ルールを持つこともできます。

## 4. 主要アルゴリズム

### 4-1. 向聴数（最重要・性能の要）

素朴な全探索では、CPUが1打牌ごとに十数回×受け入れ計算を行うため実用速度に届きませんでした
（1局あたり約200ms）。そこで **スーツ単位のメモ化＋DP合成** に変更しています。

1. 手牌を萬子・筒子・索子・字牌の4グループに分割
2. 各グループについて「取り出せる（面子数・部分形数・対子数）」の組み合わせを全列挙
3. **パレート最適でない組み合わせを削除**（3〜6通りに縮小）
4. グループ結果をキー化して**メモ化**（同じ形は二度と計算しない）
5. 4グループを状態数60以下のDPで合成し、`8 − 2×面子 − 部分形` を最小化
6. 5ブロックあって対子が1つもない場合は +1 補正

結果：**1局あたり約200ms → 約20ms（約10倍）**。
正当性は素朴な全探索実装との突き合わせ（5,000ケース完全一致）で担保しています。

### 4-2. 和了判定とオールマイティ牌

```
通常の和了判定（向聴数 === -1）
   ↓ 不成立
オールマイティ候補を抽出（白ポッチ／almighty効果を持つ特殊牌）
   ↓ 条件（リーチ時・ツモ時など）を満たすものだけ
34種類すべてに置換して和了形になるか試す
   ↓ 成立
置換結果を「どの牌の代わりに使ったか」とともに返す（UIに表示）
```

### 4-3. 点数計算

```
役判定 → 翻・符
  ＋ ドラ／赤／金／裏／北抜き／華牌ドラ
  ＋ 特殊牌の効果（ドラ+n / 翻+n）
  ＋ カスタムルールの効果
      ↓
基本点 = 符 × 2^(2+翻)（満貫以上は固定値）
  ＋ 切り上げ満貫・数え役満の開始翻数を設定で変更
  ＋ **打点ランクアップ**（華牌「夏」など）でリミットを段階的に押し上げ
      ↓
支払い分配
  ＋ 三麻のツモ損／丸取り（不足分を支払者へ均等按分し100点単位で切り上げ）
  ＋ 割れ目（当該プレイヤーが絡む支払いを倍に）
  ＋ 本場・供託
      ↓
ゲーム内ボーナス（非換金）
  ＋ 一発・裏・赤・金・白ポッチ・北・三倍満・数え役満・役満
  ＋ アリス／チューリップのめくり結果
  ＋ サイコロチャンス
```

### 4-4. 鳴きの解決順

```
打牌
 → ロン候補を収集（フリテン・同順フリテンを除外）
 → ポン・カン・チー候補を収集（三麻ではチーを生成しない）
 → 各プレイヤーの応答を集める（CPUは即時、人間は待機）
 → 優先度で解決：ロン ＞ カン・ポン ＞ チー（同格は打牌者からの近さ）
 → ダブロン／頭ハネ／三家和は設定に従う
```

### 4-5. CPU

```
1. 和了できる → 和了
2. 応答フェーズ → 鳴きの損得判定（向聴が進む＋役の目処）
3. 危険度を評価（他家リーチ＋2／3副露以上＋1）
4. 危険 かつ 自分が遠い → ベタオリ（現物＞字牌＞端牌＞筋）
5. それ以外 → 打牌候補を向聴数で絞り、受け入れ枚数−牌の価値＋安全度で採点
6. テンパイ時 → 待ちの残り枚数と打点でリーチ判断
```

難易度（beginner / normal / expert）で、リーチ基準・鳴きの緩さ・ベタオリ閾値・受け入れ重みが変わります。

## 5. 拡張の手順

### 5-1. 新しい店を追加する

```js
// src/rules/presets.js に1件足すだけ（コード変更ゼロ）
{
  id: 'store_xxx', name: '○○雀荘 ルール', category: '店舗',
  rules: { /* 既定値からの差分だけ */ }
}
```

### 5-2. 新しい特殊牌を追加する

エディタのUIから追加できます（コード不要）。データとしては：

```json
{ "id": "amethyst5p", "name": "紫5筒", "tile": "5p", "count": 1,
  "effects": [{ "type": "bonusMultiply", "value": 2 }],
  "conditions": { "menzenOnly": true } }
```

### 5-3. まったく未知のハウスルールを追加する

WHEN / IF / THEN で表現します。

```json
{ "name": "青の一撃", "when": "win",
  "if":   [{ "fact": "hasTile", "tile": "5s" }, { "fact": "riichi" }],
  "then": [{ "action": "bonus", "value": 3 }, { "action": "rankUp", "value": 1 }] }
```

表現できない場合のみ、`effects.js` に **効果の種類を1つ足す**（数行）。
ゲーム進行のコードには触れません。

## 6. テスト方針

| 層 | 手法 | 内容 |
| --- | --- | --- |
| アルゴリズム | **参照実装との突き合わせ** | 向聴数を素朴な全探索と5,000ケース比較 |
| 単体 | 期待値テスト44件 | 役・符・点数・フリテン・鳴き・流局・連荘・三麻差分・特殊ルール |
| 統合 | 対局完走テスト | 4プリセットでCPUのみの対局を終局まで実行し、点棒総和を検証 |
| 性質 | **不変条件テスト（メイン）** | 大量対局で「壊れていない」ことを検証 |
| 設定 | Validatorテスト | 全17プリセットがエラーなしで通ること／矛盾設定を検出できること |
| 表示 | 生成物テスト | 説明文に店舗固有の内容が含まれること／差分が正しく抽出されること |

### 不変条件（毎局チェック）

1. 牌の総数が一致する（手牌＋副露＋河＋北＋華＋山＋王牌 ＝ 使用牌数）
2. 同一の牌IDが2箇所に存在しない
3. 同じ牌タイプが5枚以上存在しない
4. 点棒の総和が保存される（供託込み）
5. 手牌枚数が 13 or 14（副露を含む）から外れない
6. 0翻での和了が発生しない
7. 局が進行不能にならない（ステップ上限に達しない）

**実績：1,500対局／約9,900局で全項目 0件の違反。**

### 実行

```bash
node test/run-tests.js          # 44件
node test/verify-shanten.js     # 5,000ケース
node test/sim.js 12             # 全17プリセット
node test/sim.js 300 standard4  # 約2,800局
```

## 8. 現在の技術構成と、その理由

| 項目 | 現在 | 理由 |
| --- | --- | --- |
| 言語 | 素のJavaScript（ES Modules）＋JSDoc | ビルド不要で即起動。提案の場で環境構築に失敗しない |
| 依存パッケージ | **0** | `npm install` 不要。ZIPを渡すだけで動く |
| サーバ | Node.js標準モジュールのみ40行 | 静的配信だけで足りる |
| 状態管理 | エンジン内部に集約、UIは `snapshot()` を描画するだけ | ロジックとUIの混線を防ぐ |
| テスト実行 | Node.jsから同じESMを直接import | **テストと本番で同じコードが動く** |

## 9. 将来のオンライン化方針

### 9-1. 基本原則：サーバ権威型

```
クライアント（表示・入力）
    ↓ 行動（「3索を切る」）だけを送る
サーバ（同じ engine.js を実行）
    ↓ 状態の差分を配る（自分の手牌は自分にしか送らない）
クライアント
```

- **牌山と他家の手牌をクライアントに置かない**（不正対策の基本）
- 判定（和了・鳴きの可否・点数）はすべてサーバ側で実行
- 現在のエンジンはDOMに依存していないため、**そのままサーバで動きます**

### 9-2. 段階

| 段階 | 内容 | 技術 |
| --- | --- | --- |
| 1 | 現状：ブラウザ内でCPU対戦 | — |
| 2 | ルール・店舗をDB化、成績を保存 | Supabase（PostgreSQL＋RLS） |
| 3 | 非同期の対戦（時間制限付き・観戦なし） | WebSocket（Hono/Node）＋Redis |
| 4 | リアルタイム4人対戦・観戦 | 同上＋部屋管理・再接続処理 |
| 5 | 店別ルーム・イベント・配信連携 | 同上＋配信プラットフォーム連携 |

### 9-3. オンライン化で必要になる設計

- **切断・再接続**：接続断時はCPUが代打ち。復帰時に状態を再送
- **時間制限**：1手あたりの制限時間とオート打牌
- **不正対策**：サーバ権威、行動ログの保存、複アカ検知、通報
- **リプレイ**：`engine.log` に全イベントが残るため、シードと行動列で完全再現可能
  （すでに `makeRng(seed)` による決定論的な乱数を採用済み）

### 9-4. データモデル（フェーズ2案）

```sql
stores        (id, name, area, address, hours, smoking, style, beginner_level, ...)
store_rules   (id, store_id, name, rules_json, version, published_at)
users         (id, display_name, created_at)
play_sessions (id, user_id, store_rule_id, result_json, played_at)   -- 体験ログ
checkins      (id, user_id, store_id, checked_in_at)                 -- 来店計測
badges        (id, user_id, store_id, kind, granted_at)              -- 称号（非換金）
```

`rules_json` は本試作の RuleConfig をそのまま格納できます（スキーマ互換）。
`version` を持たせ、**過去の対局がどのバージョンのルールで行われたか**を追跡できるようにします。

## 11. 開発時の注意（引き継ぎ用）

1. **エンジンに店名を書かない。** 迷ったら「設定項目として持てないか」を先に考える。
2. **効果を足す時は `effects.js` の1箇所だけ。** 進行コードには触れない。
3. **仕様を決め打ちしたら README の「置いた仮定」に追記する。**
4. **テストを先に書く。** 特にハウスルールは、実戦で滅多に出ないためテストがないと壊れても気づけない。
5. **大規模シミュレーションを回してからコミットする。** `node test/sim.js 50` が最低ライン。
